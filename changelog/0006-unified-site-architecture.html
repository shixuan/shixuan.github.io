CHANGELOG 0006 — 解耦相册与hexo

起因

相册最早直接放在 Hexo 的 source/gallery/ 下。页面里写 HTML、引入脚本，样式则在 after_render:html 中按路径插入。能用，但每加一个页面，都要再处理一次资源加载和主题配置。相册管理页加进来以后，这部分代码也跟着多了一份。

这次原本想把网站搬到 Next.js，Hexo 只负责博客。中间确实做到了单端口预览、统一构建产物，也把 Icarus 的 CSS、导航和页脚接到了 React 页面上。问题出在继续接评论、捐赠和侧边栏的时候。博客使用 Icarus 的实现，相册使用自己写的 React 实现，共享配置只能让两边拿到相同参数，组件行为仍然要分别维护。

沿着这个方向继续，需要重写相当一部分主题。以后 Icarus 升级，React 这一份也不会自动更新。为了给相册共用几个现成组件，长期维护两套页面实现不太合适。

最后撤掉了 Next.js 外壳。Hexo 和 Icarus 继续负责页面生成，相册的交互代码保留为独立模块。新增功能时，主要写模块、模板和页面声明，公共布局交给现有主题。

目录和构建关系

源码仍放在一个 npm workspace 仓库里。目录按用途分开，但网站构建只有一份最终产物。

apps/web 现在不运行 Next.js，也不生成导航和页脚。它放的是浏览器里的功能代码。apps/gallery-api 则是相册后端，两者名字相近，职责不同。

前端按功能归属分目录。browse 和 admin 各自保留 entry.jsx、page.jsx、template.html、styles.css，页面专用的组件和 hook 也放在同一目录。两页共用的请求代码放在 gallery/api.js；站点通用的挂载逻辑放在 runtime，不依赖相册。组件没有跨功能复用时，不放进全局 components 或 utils。

管理页的图片卡片、预览弹窗和说明编辑器各有一个文件，page.jsx 负责组合它们并协调操作。文件和目录使用小写连字符，React 组件使用 PascalCase，自定义 hook 使用 use 前缀。

后端的 worker.mjs 只分发路由，photos.mjs 处理图片读写，captions.mjs 处理说明及翻译，access.mjs 验证 Access JWT。部署前由 esbuild 打包为一个文件，线上 Worker 仍叫 gallery。博客保留 Hexo 约定的 source、scripts、widgets；内容维护脚本放在 tools/blog，避免被 Hexo 当作插件执行。

构建从根目录的 npm run build 开始。

先由 esbuild 打包前端模块，生成带内容哈希的资源文件名。构建脚本从输出信息里取到对应的 JS 和 CSS，再把 HTML 模板、资源链接和 front matter 拼成 Hexo 源文件。Hexo 随后处理这些页面，与博客一起生成到 apps/blog/public/。

generated-pages/ 和 assets/web/ 都是生成目录，已经加入 Git 忽略规则。需要修改页面时，回到 apps/web 编辑模板或入口。直接修改生成文件，下次构建就会被覆盖。

非hexo模块如何适配原生组件

一张相册页在浏览器里大致由这些部分组成。

相册模块只拿到自己的 DOM 容器。它不知道评论用的是 giscus，也不会去加载捐赠按钮。评论和捐赠由 Icarus 的 page 布局组合进来，博客文章使用的也是这套原生实现。

相册管理页把 comments、donate 设为 false，并设置 noindex: true。构建器会把关闭评论转换为 comment: { type: null }，关闭捐赠转换为 donates: []，写入生成页面的 front matter。开启时则使用站点公共配置。

当前生成的功能页采用单栏布局，关闭侧边栏和目录。页面声明还没有提供任意 widget 编排能力，侧边栏设置仍由 Hexo/Icarus 配置处理。

评论继续使用 giscus 的 pathname 映射，相册地址保留为 /gallery/。这次没有换评论服务，也没有迁移 discussion。以后切换到 Icarus 支持的其他评论插件，可以修改公共配置，让文章和相册一起使用新实现。评论数据是否能够迁过去，仍然取决于两个服务本身。

配置

配置 位置
站点名称、作者、导航、页脚链接、字体、评论和捐赠参数 site.config.json
文章链接格式、Markdown 处理、资源复制规则等 apps/blog/_config.yml
Icarus 默认样式、搜索、文章显示和插件设置 apps/blog/_config.icarus.yml
文章页、普通页等布局的配置 apps/blog/_config.post.yml、_config.page.yml 等
相册等功能页的入口、模板和公共组件开关 apps/web/pages.json
Icarus npm 依赖版本 apps/blog/package.json
本站的样式覆盖 apps/blog/source/css/custom.css

apps/blog/scripts/site-theme.js 负责把站点公共配置交给 Icarus。它在主题完成配置合并之后执行，补上导航、页脚和品牌信息。评论、捐赠会先看页面是否有自己的设置，没有才使用 site.config.json 中的值。因此，管理页显式关闭组件后，不会又被全局配置打开。

这层代码知道 Icarus 的配置格式。以后换主题，需要检查这部分映射，以及本站 CSS 使用的选择器。独立出来的是相册的功能代码，整个站点的页面渲染仍然依赖 Hexo 和 Icarus。

原来的自定义 widget 接入也保留了，包括 register-custom-widgets.js 对 Icarus 组件查找的扩展。这次没有顺带重写那套机制。相关实现记录在 CHANGELOG 0003，其中按路径插入相册资源的做法已经由本次构建流程替代。

浏览器运行

入口文件引入 CSS 和 React 组件，通过 mountReact 找到模板中的容器，再用 createRoot 渲染 Gallery 或 Admin。相册列表、分页、加载状态，以及管理页的文件选择、批量删除、说明编辑，都由 React 状态驱动。弹窗通过 portal 放到 document.body，避免受主题内容卡片的布局限制。

pagehide 时卸载 React root，各组件的 effect 清理函数取消请求、移除监听并销毁灯箱。pageshow 时重新挂载，处理浏览器恢复旧页面的情况。列表和说明编辑各自使用 AbortController；关闭弹窗就会取消对应请求。说明加载或翻译期间仍可编辑，返回结果不会覆盖已经改过的内容。

保留这些清理逻辑，是因为页面可能在请求期间离开，管理页还可能正在批量上传。关闭页面后，剩余上传不应继续排队，旧图片的说明也不能覆盖后来打开的图片。

灯箱管理

PhotoGrid 用 React 渲染图片节点，Justified Gallery 只调整排列所需的样式。useLightbox 在第一次点击图片时动态加载 lightGallery，在 effect 中创建和销毁实例，负责灯箱的数据追加、说明加载和事件监听。说明只读取当前及相邻图片；网格在排版完成后才观察加载下一批的位置，避免慢图导致连续预加载。灯箱的内部 DOM 仍由图片库管理，工具栏里的加载提示通过 React portal 插入。切换分段时，旧灯箱销毁完成后才创建下一个实例。

Icarus 自带图片插件，相册又使用自己的 lightGallery 和 Justified Gallery。如果两边都初始化同一片 DOM，会出现重复灯箱或布局互相覆盖。

站点接入层通过生成页面的 web_module 标记识别功能页，在这些页面上关闭 Icarus 的原生图片插件和 PJAX。相册加载自己打包的图片库，页面之间使用普通导航。博客文章仍按原来的主题配置处理图片。

目前也不支持把这些功能页任意接进另一套客户端路由。要接入 PJAX 或其他局部导航，需要另外处理模块加载和卸载时机。

问题

第一次生成相册时，图片请求和脚本都正常，但缩略图挤在一起。检查最终 HTML 才发现，源文件片段最前面的 stylesheet 链接在 Hexo 的 HTML 处理过程中丢失了，浏览器根本没有拿到相册 CSS。现在把资源链接放在一个正文容器内，随模板一起保留下来，并在输出检查里确认 CSS 链接及对应文件都存在。

另一个问题出在搜索索引。打包后的 JS、CSS 放进 source 后，被 Hexo 当成可渲染页面，连代码内容也进入了 Insight 搜索。_config.yml 的 skip_render 现在包含 assets/web/**，这些文件直接复制到发布目录，不再进入页面索引。

开发和部署

本地使用 Node.js 22，在仓库根目录运行。

预览地址是 http://localhost:3000。开发脚本先完成一次前端构建，再启动 Hexo server。esbuild 在后台监听 JS、CSS 和 HTML 模板，Hexo 监听文章及生成的页面源文件。浏览器手动刷新即可看到修改。页面声明和配置变化需要重启服务。

虽然这里有构建监听和 Hexo 两部分工作，对外只开一个 HTTP 端口。apps/blog/scripts/dev-proxy.js 把相册 API 请求转发到 Worker，GALLERY_API_ORIGIN 可以指定其他后端地址。管理操作仍需要 Cloudflare Access，启动本地预览不会自动获得线上登录状态。

生产构建输出到 apps/blog/public/，部署工具发布这个目录。相册和管理页保留 /gallery/、/gallery/admin/，API 请求继续使用已有路径。Cloudflare Worker 的路由和绑定仍在原来的位置管理，页面声明不会自动修改它们。

Decap 也继续保留。/admin/ 下的编辑器通过 skip_render 原样复制，运行自己的界面，不套 Icarus 布局。它与 /gallery/admin/ 是两个不同的后台。文章仍保存为 Markdown，登录认证由 apps/decap-auth 的 Worker 负责。

增加页面

在 apps/web/src/features/ 下放好 HTML 模板、React 组件和 JSX 入口。模板提供容器，入口导入 CSS，并调用 mountReact(容器 ID, 页面组件)。组件用 state 管理界面，外部监听、请求和图片库放在 effect 中，并提供清理函数。

随后在 pages.json 加一项，填好名称、输出路径、标题、入口和模板，选择是否需要评论、捐赠。重新构建后，它会和相册一样进入 Icarus 的页面布局。通常不需要再改 inject-css.js，也不用重新实现导航和页脚。

如果功能需要后端接口，仍然要单独实现服务并配置路由。这个构建流程只负责前端资源和静态页面。
